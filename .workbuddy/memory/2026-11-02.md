## 00:40 快车道根治：GitHub 自链（不再依赖 cron，也不碰本机）

**起因**：用户问「本机不是会占用我的内存，GitHub 怎么根本解决」。本机方案（schtasks + poll_5min.cmd）实测峰值 RSS 30.5MB、单次 17.7 秒，5 分钟一次折合平均约 1.8MB —— 确实很轻，但前提是开机且 `gh` 保持登录，用户不想走这条路。

**关键发现（这一轮真正的突破）**：GitHub 的「用 `GITHUB_TOKEN` 触发的事件不会创建新 run」有一条豁免 —— `workflow_dispatch` 和 `repository_dispatch` 都会创建新 run。写了 `self-dispatch-probe.yml` 实测：

```
dispatch HTTP 204
RESULT: built-in token was accepted for workflow_dispatch
41325248999  16:13:56  手动触发
41325256057  16:14:01  它自己触发的 ← 5 秒后
```

**于是架构从「等 cron」改成「cron 只是重启按钮」**：一次触发跑 340 分钟长班（GitHub 单 job 上限 6 小时，留 18 分钟余量给启动和收尾），班内每 6 分钟轮询一次，班末用 `GITHUB_TOKEN` 触发自己的下一班。这样对触发频率的要求从「每 5 分钟」降到「每 5.7 小时」，而实测的 cron 密度是 1 次/2.5 小时，够接续。

**两次真机试错**（都不是推理出来的，是跑出来的）：

1. 第一版 `chain` step 返回 403 `Resource not accessible by integration`。原因是 workflow 的 `permissions` 写的是 `actions: read` —— **探测能成是因为探针文件写的是 `actions: write`**。改成 write 后 204。
2. 请求 4 分钟的班实际跑了 6 分钟：`poll_loop.sh` 在最后一轮之后仍 `sleep` 满一个 interval。改成只睡到 deadline（`remaining < interval` 就睡 remaining）。

修完再测，4 分钟班准时结束并自链：

```
shift ran 4 minute(s) of a requested 4
dispatch HTTP 204
next shift queued
41326212194  16:25:00 → 16:29:06 success
41326559693  16:29:06            ← 自链产生
```

正式班 `41326641704` 16:30:06 启动，预计 22:10 结束并接下一班。

**守卫（防止把故障变成跑飞）**：实际时长不足请求的一半就不链 —— 否则一个在第 2 分钟挂掉的环会变成每几秒 dispatch 一次的循环。另外留 `chain=false` 输入，这才让链条可以 4 分钟验一次而不是等 5.7 小时。

**推送通道再次恶化**：`git push` 连续 12 次 502、`git fetch` 8 次全 502，`api.github.com` 全程可用（偶发 TLS handshake timeout，重试即过）。继续走 Git Data API。副作用：远端 main 的 commit sha 与本地不同（tree 和 message 逐字节相同）。试过用 `git hash-object -w -t commit` 复现远端对象，message 一致但 sha 仍不同（author 时间戳编码对不上），放弃。结论是接受「内容同步、sha 并行」，`work/push_via_api.py` 每次以远端 head 作 parent，续推不受影响。API 提交已显式传 noreply 的 author/committer，没有再泄漏主邮箱。

**尚未验证的风险（如实记录，不当结论）**：链条意味着 24 小时持续占用一个 runner。公开仓不计费，但 GitHub 的 fair-use 政策对「与项目无关的持续计算」有解释空间；我无法从 API 判断它是否会被限。若被限，退路是 cron（2.9% 但每次都能重启链条）或把班次限制在若干小时窗口内。
