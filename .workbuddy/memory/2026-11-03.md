## 00:20 复查「能不能确保不再发垃圾」：又找到两个口子

用户问能不能确保。没有直接答「能」，把出口逐条查了一遍，结论是**还不能**，当场补掉。

**口子一：渲染只堵了 URL，标题和 labels 还是裸的。** `render()` 在 11-02 那次已经把 `html_url` 去掉，但 `[{labels}] {it['title']}` 仍是原文插入。标题是上游仓库里别人写的任意字符串：

- 带 `@某人` → 真通知到真人；
- 带 `owner/repo#num` → 在对方 issue 生成 cross-reference 并戳全部 watcher。

同一个错换了条路。修法不是「记得哪个字段有链接」，而是**逐字段封闭**：新增 `code()`，先剥反引号（防标题里的 `` ` `` 提前闭合 span）再包一层 code span。实测 5 类恶意标题（mention+ref / URL / 带反引号 / 尾部反引号 / 普通），**剔除 code span 后裸 mention、裸 ref、裸 URL 均为 0**。

验证方法本身踩过一次：第一版检查用 `(?<!`)` 看前一位字符，把 code span 内的内容也算成「裸的」，误报 FAIL。正确做法是先剥掉 code span 再做正则。

**口子二：解析自己的台账时把标题里的编号当成条目。** `KEY_RE` 原来整行搜跨仓编号，标题里出现一个就会被记进 `seen`，之后**静默跳过另一条真实 issue**。改成锚定行首 + 限定本工具写的格式。`inbox.py` 的 `LINE_RE` 还停在「带尾部 URL」的旧格式（`render()` 早就不写 URL 了），已同步。

**顺带查了 commit message 这个出口**（本地全量 190 个提交）：4 处命中跨仓编号，逐个看原文——`foo/bar#1` 在反引号内且仓不存在、`5007/psutil` 不是合法 owner、`mcp/servers` 不是真 slug（真名 modelcontextprotocol/servers），只有 `explosion/preshed#56` 指向真实仓库，而那是我自己开的 PR。**结论：这条出口目前没外溢，但它是我常犯的写法，已写进规则。**
