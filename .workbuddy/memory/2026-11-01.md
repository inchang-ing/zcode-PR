### 规律 1：缺陷的「同一字符两层语义矛盾」形态
- 当一个字符在 A 层被当作**分隔符**、在 B 层被当作**内容/分组符**时，A 层会先吃掉 B 层需要的信息，且 B 层看起来完全正确、难以从日志发现。
- 判据：修之前先查 B 层**已有的常量表**。若 B 层已把这些字符列为合法内容，则缺陷点确定在 A 层的切分/正则，而不是 B 层的解析能力。
- 修法：让 A 层**排除** B 层认可的内容字符（而不是在 B 层补解析）。这样改动最小、语义最一致。
- 例：`inspect_ai#6223` —— `scorer/_common.py` 的 `re.split(r"\s+")` 把 `"2 500"` 拆成 `['2','500.']`，而 `scorer/_unicode.py` 的 `_GROUP_SEPARATORS` **已包含** U+00A0/U+202F/U+2009；正解是分词正则改 `[^\S\u00a0\u202f\u2009\u2007\u2008]+`，让数字保持单 token。

### 规律 14：「等一个事件」式启动挂起，正确形态是「等事件 或 提供该事件的任务结束」
`__aenter__` 只 `await ready.wait()`，而 set ready 的那个 loop 已异常退出（异常还被自己 `except` 吞成日志）→ 永久挂起。通用修法三条：①`asyncio.wait({waiter, producer_task}, FIRST_COMPLETED)` 同时观察两者，producer 先结束就取它的异常抛出；②**不要**在 producer 的异常处理器里置位 ready —— 那是把失败伪装成成功；③`__aenter__` 抛错时 `__aexit__` 不会被调用，清理（cancel 任务、关闭子队列）必须由失败路径自己做。若内层吞异常，需额外用属性（`_loop_error`）把异常带出来，否则外层只能看到无信息的 RuntimeError。

### 规律 15：判断「测试失败是不是我造成的」，比失败集合本身而不是失败数量
本次相邻模块 14+4 条失败全部来自 fakeredis 版本漂移。做法：同一命令在**修前/修后各跑一次**，`grep '^FAILED' | sort` 后 `diff`，完全一致即可判定环境既有问题。比逐条读 traceback 快一个数量级，也比「看起来都是 redis 相关」可靠。

### 规律 16：下游扩展的测试套件是真实兼容性的唯一探针，且必须做 baseline 对照
markdown#1666 的维护者（同时是 Pymdown Extensions 作者）只说「在 pymdown 里跑出两个失败」，没给细节。把 pymdown 全套跑两遍（markdown master `b41e0aa` vs 我的分支，同一棵 pymdown、同一 Python）：**13 failed vs 15 failed，差集正好 2 个**，且两处差异都只是 4 个空格缩进。只报「2 个失败」没有信息量；报「差集 2 个 + 其余 13 个是既有版本漂移」才可行动。方法同规律 15：`grep '^FAILED' | sed 's/ - .*//' | sort` 后 `comm -13`。
定位手法：用 `PYTHONPATH` 切换两份 markdown 副本（`git worktree add` 建 master 对照树），避免污染工作区；再用自定义 `Preprocessor` 打印「进入核心的原始行」，确认两版输入逐字相同 → 差异只可能在 `HTMLExtractor`。

### 规律 21：弱签名探测器的正解是「用带校验和的解析器确认」，不是「改成更信扩展名」

## 19:59 轮 — 0 认领；无 git 时用 Git Data API 造双父 merge commit 解冲突

- **无 git 出网 ≠ 不能推代码**：本机 `github.com:443` 被封（20s 超时，curl 返回 000），但 `api.github.com` 与 `codeload.github.com` 都通。完整替代通道 = `POST /git/blobs`（逐文件建 blob）→ `POST /git/trees`（`base_tree` 取目标侧树）→ `POST /git/commits`（`parents=[我方head, 上游head]`）→ `PATCH /git/refs/heads/<branch> force=false`。这条通道**天然写出正确双父 merge commit**，比 Contents API 单父提交更对：merge-base 前移后 PR diff 不会掺入上游改动（本轮 zarr#4526 解冲突后仍是 12 文件 / 242+ / 8-，干净）。`codeload` 还能按任意 sha 拉 tarball，可用来重建工作树跑测试。
- **`codeload` + 逐文件 API 取三方版本是「无 clone 也能三方合并」的通用手法**：`git merge-file -L ours -L base -L main` 完全不需要仓库历史，只要 base/ours/theirs 三份文件。定位 base 用「我方 head 若是 merge commit，其第二父就是上次合并时的上游 head」。
- **仓库改名会让 cross-ref 的 `full_name` 与调用时的旧 slug 不一致**（`all-hands-ai/openhands#19177` 的 cross-ref 报 `OpenHands/OpenHands#19178`）。判同仓不能做字符串相等，要看「是否指向本仓对象」——否则会把自家竞品 PR 当成「他仓引用=正信号」放过。另：改名仓用旧 slug 打 `search/issues` 会 422，需用 canonical name。
- **对面是 agent 的 issue 可一眼判死**：`AI-WATERMARK` 段写 `Scope: ... wrote the proposed fix and the regression tests, ran the commands`，或标签 `ai-generated` + 正文给"Proposed fix"，等价于「作者自陈已有补丁」。本轮 opik 两条、metagpt、open-interpreter 四条都属此类，比逐条五项核查快得多。
- **「合并后测试数变少」不能直接判丢失**：main 侧把 5 条硬编码版本号的用例改写成 `CAST_VALUE_RS_MIN_VERSION` 参数化（49→44 条）。判据是 `diff ours merged` —— 若差异恰好等于上游那笔预期的改写，就是合并正确；用数量比会误判。
