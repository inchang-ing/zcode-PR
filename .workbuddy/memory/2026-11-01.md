### 规律 1：缺陷的「同一字符两层语义矛盾」形态
- 当一个字符在 A 层被当作**分隔符**、在 B 层被当作**内容/分组符**时，A 层会先吃掉 B 层需要的信息，且 B 层看起来完全正确、难以从日志发现。
- 判据：修之前先查 B 层**已有的常量表**。若 B 层已把这些字符列为合法内容，则缺陷点确定在 A 层的切分/正则，而不是 B 层的解析能力。
- 修法：让 A 层**排除** B 层认可的内容字符（而不是在 B 层补解析）。这样改动最小、语义最一致。
- 例：`inspect_ai#6223` —— `scorer/_common.py` 的 `re.split(r"\s+")` 把 `"2 500"` 拆成 `['2','500.']`，而 `scorer/_unicode.py` 的 `_GROUP_SEPARATORS` **已包含** U+00A0/U+202F/U+2009；正解是分词正则改 `[^\S\u00a0\u202f\u2009\u2007\u2008]+`，让数字保持单 token。

### 规律 4：`bot 自动关闭` ≠ `维护者裁定`，需要分开处理
- 判据：看关闭者与关闭理由。`github-actions[bot]` 关且正文带**可执行指令**（如 *"Please create a new PR using the template and complete the checklist"*）→ 属流程问题、可救济；`maintainer` 关或 issue 被 `not_planned` → 真裁定、不申诉。
- **坑**：bot 关掉的 PR，作者调 `gh pr reopen` 会被拒（`GraphQL: Could not open the pull request`），只能新建。
- 新建前**必须重做撞车核查**（相当于换了个 PR 号重新出手）：查 issue 是否仍 OPEN、有无 assignee/标签、`search/issues?q=repo:X+is:pr+is:open+N+in:body` 有无他人引用。本例 `any-agent#967` 全清 → 才新建 #969。
