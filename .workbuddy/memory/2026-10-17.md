## litellm#46262：CI 红定位与修复（当日最大动作）

上一轮推送后 `gh pr checks` 发现两个失败：`lint`（3 秒即败）与 `python`（3m24s）。

- **`lint` 是汇总作业**（"Require every lint job to succeed"），真失败在它依赖的 `python` 作业——`--log-failed` 里能直接看到 NEEDS 依赖树，别被作业名骗。
- **根因**：type_discipline_gate 报 `LIT006: total 1005 over ceiling 1004 (this change added 1)`，位置 `streaming_chunk_builder_utils.py:1396`。拉取 PR 头文件核对：`parts: Final = cast("Sequence[Mapping[str, str]]", content)` **没有同行的 `# cast-ok:` 注释**——上一轮「本地补了 cast-ok」的结论是有痕的，但 API 推送用的 blob 里注释丢了（本地 git 分支还是 rebase 前的旧提交 `faeb86d`，真相只在 CI）。
- **修法**：读透门禁三件套（`type_discipline_gate.py` / `check_type_discipline.py` / `lint_base_counts.py`）确认机制：LIT006 报在 cast 首行，同行 `# cast-ok: <reason>`（≥3 字符）才抑制；LIT013 专抓「抑制空气」；ceiling 来自 CI artifact（下载 `type-discipline-counts-*.json` 实测 LIT006=1004）。
- **关键发现——门禁扫描范围**：type_discipline_gate 的 `TARGET = "litellm"`，**只扫 litellm 包，不含 tests/**。本地初版对比把 tests/ 算进去，多出一个 LIT010 +2 的**假 breach**（两条新非 Final 赋值都在测试文件里）；test_quality_gate 的 TARGET 才是 `tests`（TQ 规则，实测零增长）。按真实 target 重比：LIT006 15→15，全规则零增长。
- **推送**：Git Data API（blob→tree→commit→ref），blob sha 与本地 `git hash-object` 逐字节一致（`b6ef7eab`），LF 校验 0 CR；先推成 2 提交，再压回单干净提交 `b19363b7`（parent 直接接 main `ef1cb19`，作者/日期原样保留）。
- **结果**：新 commit 上 type-discipline ✓、test-quality ✓、ruff format/lint/strict ✓、basedpyright ✓、循环 import/import safety ✓；82 项检查全绿（仅 mcp-elicitation pending）。
